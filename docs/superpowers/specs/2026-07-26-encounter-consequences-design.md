# 情景行动驱动的遭遇调整：设计说明

## 目标与边界

本阶段把游戏推进台中记录的玩家行动转化为可审核、可应用、可撤销的
遭遇配置变化。完成后，“玩家提前破坏仪式”不再只把难度标签降低一级，
而会形成例如“移除第二轮增援”“首领获得‘无法召唤阴影’状态”
“两名守卫不参加本次遭遇”
这样的结构化草案。只有 DM 确认后才修改战斗。

本阶段包含：

- 从当前场景、在场角色、怪物和最近推进记录生成调整草案。
- 支持五类有限操作：移除参战者、增加参战者、调整 HP、设置状态、
  设置增援轮次。
- 预览变更前后差异。
- DM 确认后在一个数据库事务中应用全部操作并写审计记录。
- 支持在战斗尚未结算经验前撤销最近一次调整。
- 战斗页面解释每项调整的来源和实际影响。

本阶段不包含：

- 完整职业成长库。
- 完整施法、装备、光照和战争迷雾规则。
- 玩家端独立界面。
- AI 自由生成任意数据库操作。

这些内容继续拆成后续独立阶段，避免同时修改过多规则核心。

## 方案比较

### 方案 A：继续只保存难度级别

优点是改动最小。缺点是战斗中的怪物、能力和增援没有任何变化，无法满足
“玩家准备真正产生后果”的目标，因此不采用。

### 方案 B：让前端直接执行一组 CRUD

优点是开发快。缺点是执行到一半失败时会产生部分修改，也难以可靠撤销；
刷新页面或重复点击还可能重复应用。因此不采用。

### 方案 C：结构化草案 + 后端事务确认

AI 只能返回固定操作类型。后端验证所有目标均属于同一战役和场景，
一次性应用修改、更新草案状态并写审计记录。撤销使用确认时保存的反向操作。

采用方案 C。它符合项目现有的“AI 提议、DM 确认、结构化状态为真相来源”
原则，也能为以后任务奖励、交易和战斗结算事务复用同一模式。

## 数据模型

新增 `encounter_adjustment_proposals`：

- `id`, `campaign_id`, `scene_id`, `combat_id`；尚未创建战斗时 `combat_id` 为空
- `source_event_id`：触发建议的推进事件
- `title`, `reason`
- `difficulty_shift`：`-1`, `0`, `1`
- `operations_json`：有限操作数组
- `inverse_operations_json`：确认时由后端生成
- `status`：`pending`, `applied`, `rejected`, `reverted`, `conflict`
- `applied_at`, `reverted_at`
- 通用时间戳和版本号

操作采用带判别字段的 JSON：

```json
{
  "kind": "remove_entity",
  "entity_type": "monster",
  "entity_id": "uuid",
  "reason": "玩家提前封锁侧门，守卫无法赶到"
}
```

允许的操作：

1. `remove_entity`
2. `add_scene_entity`
3. `set_entity_hp`
4. `add_entity_condition`
5. `schedule_reinforcement`

`schedule_reinforcement` 暂存在战斗的结构化调整列表中，到指定轮次时显示醒目
提示并由 DM 点击“部署增援”。本阶段不自动替 DM 推进回合或生成掷骰。

## 生成与确认流程

1. DM 在推进台记录玩家行动。
2. 本地模型读取当前场景、最近事件、当前参与者和原子库。
3. 模型返回严格 JSON 草案；服务端进行 Pydantic 校验。
4. 若模型失败或引用不存在的实体，返回可操作错误，不写状态。
5. 推进台显示原因、难度变化和每项具体操作。
6. DM 可删除单项操作或拒绝整份草案。
7. DM 确认后，后端锁定 `pending` 草案，验证版本与归属，并将其标记为
   当前场景已应用的遭遇配置。如果场景已有进行中的战斗，同一事务立即修改
   战斗员；如果尚未创建战斗，`startSceneCombat` 在创建战斗员时应用配置。
8. 战斗页读取已应用草案，显示“原因 → 实际变化”。同一草案只对一个战斗
   生效；首次创建战斗后写回 `combat_id`，避免后续战斗重复套用。
9. 经验尚未发放时，DM 可以撤销；后端执行反向操作并记录审计。

## 规则与安全约束

- 使用 D&D 5e 2024 作为默认规则。
- 本地模型继续使用现有 `qwen3:30b-instruct`，`think=false`。
- 不下载模型，不调用云服务。
- AI 不直接写数据库。
- 一份草案最多 8 项操作。
- HP 只能在 `0..max_hp` 之间。
- 不允许删除角色原子、NPC 原子或怪物原子；只改变本次战斗参与状态。
- 不允许把其他战役实体加入当前战斗。
- 已发放经验的战斗禁止撤销配置，以免破坏结算依据。
- 重复确认、拒绝和撤销必须幂等。
- 版本冲突时标记 `conflict`，不执行部分修改。

## 前端设计

推进台新增“遭遇后果草案”面板：

- 顶部显示触发行动、AI理由和建议难度变化。
- 中间按操作显示自然语言差异：
  - “移除：异教守卫 ×2”
  - “首领 HP：68 → 48”
  - “添加状态：无法召唤阴影”
- DM 可逐项取消勾选。
- 操作为“拒绝”“确认应用”。

战斗页新增“情景后果”区域：

- 显示已应用草案。
- 区分推进台情景修正和 DM 手动调整。
- 有待部署增援时显示目标轮次与“部署”按钮。
- 在允许范围内提供“撤销最近调整”。

不新增新的主导航页面，避免工作流分散。

## 错误处理

- 模型不可用：保留 DM 事件，提示可以手动创建调整草案。
- JSON 无效：进行一次有限修复；仍失败则不保存草案。
- 引用过期：确认时返回冲突，前端刷新参与者并要求重新审核。
- 事务失败：草案仍为 `pending`，战斗状态不发生部分变化。
- 撤销冲突：保留已应用状态并显示具体冲突实体。

## 测试策略

后端：

- 严格操作 schema 单元测试。
- 跨战役引用被拒绝。
- 确认事务全部成功或全部回滚。
- 重复确认幂等。
- 已结算战斗禁止撤销。
- 撤销恢复 HP、状态和参与者。

前端：

- 草案解析和差异文案单元测试。
- 未确认前不调用应用接口。
- 应用后刷新事件、场景参与者、战斗和战斗员。
- 冲突、模型不可用和空草案提示。

完整门禁：

- Ruff、严格 Mypy、Pytest。
- ESLint、TypeScript、Vitest、Vite build。
- Alembic 从空库升级及现有本地库升级。
- 浏览器验证推进台生成/确认草案并在战斗页看到实际变化。
